# Forever Planner: project guide

Read this before changing anything. It explains what the planner is for, how it is built, and which decisions are settled. User-facing features are in `README.md`; release history is in `CHANGELOG.md`.

## Intention

A gear, leveling and crafting planner for **WoW: Forever** characters. It exists because GearQuest (the in-game addon) is awkward to use, sometimes fails to rank gear for feral druids, and only judges items you have just looted. The planner answers "what should I go get next, and where?" based on your character, your leveling path and your gold.

Its users are an experienced player and a brand-new player, so **simplicity beats configurability**:

- No stat-weight knobs. Weights come from spec presets plus a single Questing / Dungeons choice. Questing halves hit and expertise (same-level mobs need far less hit than the bosses the presets are tuned for). Questing on a PvP-ruleset character, read from the profile, also gives Stamina at least 60% of the spec's main-stat weight; dungeons use the presets as they are.
- Specs are detected from talents. Main/off spec is one selector, plus cat/bear for feral druids.
- Every UI choice should be something a new player understands without reading docs.
- Suggestions must be things you can actually get: right faction and class, a known source, reputation within reach, quests not yet completed, a zone on your path.

## Architecture

A static site built with Vite from `web/` and served by GitHub Pages. There is no server.

- **Built with TypeScript + Vue 3** (migrated step by step on 2026-11-27, v0.46–v0.69): Vite pipeline, typed logic modules with tests, typed Questie reader, all UI in Vue, and a reactive store.
- **The store (`state.ts`):** `state` is a Vue `reactive` object, so views redraw by themselves when what they read changes. Rules that keep it correct and fast:
  - Game data and results (`questie`, `tsm`, `inventory`, `upgradeOptions`, `upgradesBySlot`, the picks) are `shallowRef`s inside it: always replace them whole, never edit them in place; they stay raw (no proxies over the Questie database) and replacing them redraws. Character snapshots are `markRaw`ed per key for the same reason (`loadState`, `refreshCharacter`).
  - Settings, characters (with their route and gear plan), `tooltipRequirements`, `routeEditor` and the crafting tool's list are deeply reactive: edit them in place.
  - A computed only sees reactive reads. Never let one depend on something outside the store (localStorage, a module variable): pass it in instead. Example: `vendorDiscountRate(rank)` takes the Bartering rank, because reading it from storage left the crafting plan stale. The source cache in `sources.ts` hides what a source list depends on (TSM, Questie, your inventory), so card computeds read `props.candidate` (a new object on every ranking) rather than the item, which stays the same object across rankings.
  - Ranking still runs in `render()` (`gear.ts`), called by every action that changes what counts; it clears the source caches, so call it after such changes rather than relying on reactivity to re-rank.
  - Check every UI change in a real browser, both themes, with no console errors; run `npx vite` once to see Vue's dev warnings, which production builds hide.
- All code is in `web/src/` (TypeScript, Vue SFCs); the page entries are `main.ts` (gear) and `crafting.ts`. `web/public/` holds only data that Vite copies as-is: `game-rules.js`, `zone-guide.js`, `data/*.js` and the maps, loaded as plain `<script>` tags before the entry (Vite's "can't be bundled" warnings for those tags are expected). Each page mounts its Vue roots on `display: contents` wrappers (`#gear-page`, `#crafting-page`) so the page grid stays as it was.
- **The browser calls the Battle.net API directly** with the user's own API client. Profile requests use `cache: "no-cache"`: Battle.net sends only a `Last-Modified` header, so browsers otherwise reuse a stale profile for a while (about 10% of its age) and Refresh showed an hours-old logout. The secret lives only in `localStorage`. Battle.net rejects `Origin: null`, so the site must be served over HTTP, never opened as `file://`.
- **Local WoW files** are read through the File System Access API, from a picked `World of Warcraft` or `_forever_` folder whose handle is kept in IndexedDB. The files are read, never uploaded.
  - Questie (`QuestieDB_Forever.toc`, base64 CBOR records, plus `support/Forever/Zones/dungeons.lua`) supplies item sources, quest data and dungeon entrances.
  - TradeSkillMaster supplies prices (`TradeSkillMaster_AppHelper/AppData.lua`, base-32 copper) and inventory (`WTF/Account/*/SavedVariables/TradeSkillMaster.lua`).
- **The wowsims/forever item database** (`assets/database/db.json`, MIT) fills in the items Forever hides from Battle.net and the game files until players discover them (new Forever items, and many relocated Classic ones). `data/build.py` adds every phase 1 item it has that Battle.net doesn't, marked `fromSimulator`, with quest and reputation sources; drops and vendors for them come from Questie at runtime like for any other item. Their icons come from Wowhead's icon CDN by name.
- **Wowhead** is used for three things only:
  - the nether tooltip API, to fill in reputation requirements that Battle.net omits (cached 14 days, failures retried after 1 day);
  - the level each recipe is learned at, which is the start of its orange range (`tools/build-recipe-levels.js` reads the recipe list on each Forever profession page in a headless browser). Everything else comes from the game files: a Battle.net recipe ID is a `SkillLineAbility` ID, which gives yellow and grey; green is halfway between, as in the game; recipes with `AcquireMethod` 1 come with the profession and are learned at 1. Wowhead's orange 0 means no orange range (its `learnedat` then equals yellow); recipes Wowhead has no colors for also start at yellow. The builder refuses to write if more than 5% of recipes disagree with the game files on yellow or grey (79 of 2195 did in 2026-11, mostly late Blacksmithing);
  - outbound links to `https://www.wowhead.com/forever/{item|quest|npc}=ID`.

### Data rebuilds

1. `python3 -I data/build.py` needs `~/.config/blizzard-api.env` with `BLIZZARD_CLIENT_ID` and `BLIZZARD_CLIENT_SECRET`.
2. Then `node tools/build-maps.js`, which needs `npm install` for `jpeg-js`.
3. Then `node tools/build-recipe-levels.js`, which needs a Chromium for `playwright-core` (`npx playwright install chromium-headless-shell`, or point `CHROME` at one). Wowhead pages are cached 30 days in `data/cache/wowhead/`.

All three cache their downloads in `data/cache/`, which is not committed. wago tables are cached per game build (`data/cache/wago/<build>/`, one build per run), the wowsims database per commit (`SIMULATOR_COMMIT` in `build.py`; bump it to pick up newly discovered items), and Battle.net "not found" answers are retried after 7 days because Forever reveals items over time. Outputs are written only after everything has been built.

wago.tools returns 403 without a User-Agent and 429 when hit too fast. The builders send a User-Agent and throttle with retries.

Battle.net Forever namespaces are `static-forever-{region}`, `profile-forever-{region}` and `dynamic-forever-{region}`. Characters are looked up as `{name}-{surname}`.

## Settled decisions (don't reopen without a reason)

- **Hosted on GitHub Pages.** Not an extension, an exe, a `.bat`, a server or a Claude artifact. The players use Chrome on Windows and must not need any tooling.
- **No QuestieDB data in the repo.** Its licence is unclear, so it is always read from the user's own install. Fetching it from GitHub instead was checked on 2026-11-27 and rejected: the packaged release (`QuestieDB-<version>-Forever.zip`, with the baked `QuestieDB_Forever.toc`) can't be downloaded by a browser (GitHub's release file server sends no CORS header), and the raw source files in the repo lack the new Forever content and Questie's corrections (no Eye of Mugg; about a third of quests with different levels or quest givers). Publishing the release with our site would redistribute it.
- **Zone level ranges come from Icy Veins' guide, not from Questie quest levels.** Ranges derived from Questie were tried and rejected because they disagree with how people actually level. The one exception, Mount Hyjal, is kept at 55–60.
- **Reputation items are suggested only within one standing of the current one.** Grinding reputation is slower than levelling to the next item.
- **Physical specs only get the best armor type their class wears at that level** (`bestArmorOnly` on the spec in `game-rules.js`, checked by `suitsSpec` at the level the item would be worn): leather for rogues and ferals, leather then mail from 40 for hunters and Enhancement, mail then plate from 40 for Arms, Fury, Protection and Retribution. Casters and healers (Resto, Balance, Holy, Elemental, Restoration shaman) are exempt: an Intellect piece of a lighter type is often their better choice. Why: Forever's spell data has no armor specialization and Cat Form doesn't change armor, so DPS weights ignore armor, but Bear Form multiplies gear armor by 2.8 (Dire Bear 4.6) and lighter armor is a real loss for melee. Cloaks and untyped pieces are unaffected.
- **Mail and Plate are trained at level 40** (`armorFromLevel` in `classProficiencies`; Forever confirmed for hunters and shamans, and no plate exists below item level 40). `itemUsableLevel` raises such items to 40, so they show as level-40 upgrades before that.
- **Only the selected spec counts.** The main/off selector switches the whole gear page to that spec; the other spec's gains are never shown.
- **Quest chains are prerequisite trees, not lines.** A quest pick in the gear plan shows every quest whose prerequisites are done (`QUESTIE.availableSteps`), never a single "step N of M". Battle.net can't see the quest log, so completed quests are the only progress signal.
- **The gear plan replaces the old quest and crafting lists** (v0.77.0). You click upgrade cards to pick them, any number per slot. **Each spec has its own plan, feral cat and bear included** (`character.plans`: spec key from `activeSpec` → slot → list of picks, each an item and random suffix); the plan panel and the paper doll show the plan of the spec you're gearing. The single shared plan used before v0.81.0 (`character.plan`) moves to the spec active at the next start. Refresh prunes every spec's plan against that spec's weights. The plan, under the leveling path in the sidebar, groups picks by where to get them: Buy on the auction house and then Craft first, since you can do both right away (Craft has "Craft all"), then route zones in path order each followed by its dungeons, then other zones (their dungeons next to them). Vendor buys go under the vendor's zone, because a vendor can be across the world. The paper doll marks slots with a pick (accent ✓ instead of the green ▲). Old quest lists and the crafting cart were moved into plans once (`moveOldListsIntoPlans`).
- **Refresh prunes the plan:** picks you've equipped, or that are no longer an upgrade over what you wear.
- **Upgrades are listed biggest improvement first**, by each slot's best gain. An upgrade that needs a level or two isn't discounted: the lookahead already keeps it close, and the quicker option on the same card covers "what can I use now". (Until v0.74.0 such upgrades counted half, which buried big ones.)
- **Gains are also shown as a share of your whole gear** (`gearScore`: what every equipped piece is worth with the current weights), e.g. "+72.1 attack power (+9.5%)". A share of the slot's own item was rejected (twice): the weapon holds about half of a melee character's worth, so other slots showed absurd percentages (a ring +330%, the best weapon +19%) and a per-slot bar would hide real weapon upgrades while keeping tiny necklaces. **Upgrades under 2% of the whole gear are not suggested** (`isWorthwhileGain`, raised from 1% in v0.78.0), a fixed rule chosen over a setting; it scales with the character, so tiny upgrades disappear as gear improves. The same bar decides whether a hidden item or skipped dungeon still has an upgrade.
- **Free upgrades on your leveling path always count.** A quest reward or named-mob drop in a zone on the active route (not a dungeon leg) only needs half the bar, 1% (`FREE_ON_PATH_GEAR_SHARE`, `isFreeOnRoute`): you'll get it anyway, but tiny ones aren't worth a card. When neither the best nor the quicker pick is such an item, the card adds a third pick, "On your way" (`onTheWay`), which also takes part in ring/trinket pairing.
- **What you already have counts.** Gear in the bags, bank or mailbox of any character on the same realm type and faction (from TSM's inventory) is an `owned` source: free, usable now, shown first on the card ("You have it, in your bank" / "on Bank Alt…: mail it over") and in a "You have it" group at the top of the plan. Bind-on-pickup gear on another character doesn't count (it can't be mailed). Materials you have do NOT lower a craft's cost on cards or in the plan: they're worth their market price (you could sell them), and the point is to compare crafting with the AH fairly (tried in v0.80.0, reverted in v0.80.1). Only the crafting tool's own "use what I have" mode uses them.
- **Every slot pairs a best upgrade with a quicker option you can reach now.** Rings and trinkets are paired so both picks never come from the same quest.
- **Stat weights come from the Forever simulator, wowsims/forever** (`ui/specs/*/presets.ts` and `ui/specs/druid/feral_ep.ts`, taken at commit 510f0a8). Each preset is the sim's weights scaled so one unit is 1 attack power, spell power, healing or stamina, and that unit is shown on the gain badge. Weapon DPS is weighed per slot: main hand, off hand and ranged. Never use Classic assumptions; in Forever, for example, feral form attacks use weapon DPS.
  - Taken directly: cat and bear, Arms, Fury, Prot warrior, the three rogue specs, Ret ("Unsealed Wrath"), Enhancement, Elemental, Shadow, Holy and Disc priest ("single target"), Balance, hunters (BM and MM use "Turret", Survival uses "Melee").
  - Borrowed, because the sim has no weights for them: Holy paladin, Resto druid and Resto shaman use the Holy priest weights; Prot paladin uses Prot warrior's; mages and warlocks use Balance's caster weights with their own school damage, plus Elemental's Spell Piercing weight for warlocks (Method's Forever guides rank it high for them). Replace these when the sim adds those specs.
- **Random-suffix items are scored as their best suffix for the selected spec.** The card names that suffix and links to it on Wowhead. Suffix stats come from the game files (`ItemXBonusTree` → `ItemBonus`, scaled by `RandPropPoints`); the roll chances are not in them, so none are shown.
- **Each character has a "Max gold per upgrade".** An upgrade whose cheapest way to get it (AH price, vendor price or crafting materials; quests and farmable drops are free) costs more is hidden from both cards, and an AH listing above it doesn't count as an easy source. AH prices also show the gold per point of gain ("≈ 26s per attack power"); gain per gold is shown, never used to rank, because ranking by it favours free and tiny upgrades.
- **The auction house is not a source for random-suffix items.** TSM keeps one price per item for every suffix together (checked against a real `AppData.lua`: only plain item IDs, the `::i1` variants are item levels), so it can't say whether the suffix we suggest is listed or what it costs. Their cards show "AH … for any suffix" for information only; crafting, quests and drops still count.
- **Drops from more than 3 different creatures are not a way to get an item.** Questie has no drop chances, so many creatures (trash, world drops) stands in for a low chance that you shouldn't farm. Containers (chests and the like) don't count either; their loot chances are as low. Such items count only when they're on the AH, and then their card says "Buy it on the auction house (N listed)" instead of listing the drops and chests, which would read as "go farm this". Boss, rare and named-mob drops still count as free. The crafting tool keeps listing them as material sources.
- **The dungeon list comes from the game's dungeon finder table (`LFGDungeons`, type 0), not from a website.** It has exactly Forever's dungeons plus the four classic raids; wings are merged into one entry per instance, and each entry's minimum level comes from its `ContentTuning`. `build.py` keeps only the game-data quirks by hand: name fixes ("Zul'Farak", "Stormwind Stockades") and extra area names Battle.net and Questie use. Each dungeon's quests are the Battle.net quest area of the same name. Don't reintroduce a hand-maintained dungeon list.
- **Every dungeon counts automatically**, on the leveling path or not: its boss/rare drops and its quests count from its game level. That level is the game's own minimum, not the highest quest level: one late quest (Sunken Temple, BRD and Dire Maul each have a level 60 one) would push the whole dungeon to 60; each quest still counts from its own level. The player opts out instead of in: "Skip <dungeon>" on an upgrade card adds it to `character.skippedDungeons`, which removes its drops and quests (`obtainableSources`). There is no dungeon list or per-zone dungeon checkbox; adding dungeons one by one was too much work and made the panel too long.
- **Hiding is undoable and self-cleaning.** "Not interested" and "Skip" show an Undo line right away. On Refresh, hidden items that aren't an upgrade for any of the character's specs, and skipped dungeons without upgrades left, are dropped from the list (`pruneNotInterested`).
- **Upgrade cards show only sources, the region-average AH price and the crafted price.** Recipe knowledge belongs in the crafting tool.
- **The crafting tool shares your materials down the list** (`sharesMaterials`, on by default, a checkbox saved with the crafting settings): items are planned in list order from one pool of your characters' materials, so the first craft takes them and later ones get what's left; switched off, each item is planned as if all your materials were for it. Crafts can be reordered with ↑ ↓. Items that need no crafting (cheaper to buy ready-made, or already in your bags) are shown first in their own group and have no arrows.
- **The profession guide picks, at every skill point, the learnable recipe with the lowest expected cost per point** (material cost ÷ skill-up chance, plus a pattern's price spread over the points it covers), keeping the current recipe unless another is more than 10% cheaper so the steps don't flip back and forth. The chance is 1 while orange, then (grey − skill) / (grey − yellow), the classic formula. Recipes are chosen with materials priced like the crafting tool prices them (vendor, AH or crafting, whichever is cheapest) at market price; a material that's cheaper to craft but only by a profession the character lacks is priced at its buy price (`buildGuide`'s `canCraft`). The choice doesn't know what the character owns. The stage buy lists are then planned by the crafting tool's own planner (`planStepMaterials` → `planEntries`), the steps left in order with one shared stock: your characters' materials first (same character choices as the crafting tool), then crafting where it's cheaper and the character has that profession (else buying; an override of "buy" means own first, then buy), so a cheaper-to-craft material shows as its own materials plus a "Craft first" line on the step. These lists use today's prices; the stage costs stay the plan's. A recipe counts if it's known (Battle.net), trained, or taught by a pattern with a vendor or AH price. Trainer fees aren't in any data and aren't counted. Like gw2crafts, a plan is saved (`character.professionGuides[profession]`: the guide with that day's prices, ticked steps and bought materials) so you can buy first and carry on; "Make a new plan" replaces it. `recipes.js` also has recipes that make no item (`itemId: null`: the enchants, a few engineering tinkers); the crafting tool's recipe index skips them, the guide names them from `FOREVER_RECIPE_NAMES`.
- **Profession tools come from the game files.** `data/build.py` adds each recipe's required tool categories (`SpellTotems` via `SkillLineAbility`: rods, Blacksmith Hammer, Arclight Spanner, …) and writes `tools.js` (`FOREVER_TOOLS`: each category's type, mask and its named item; every item that counts as one). A tool covers a requirement when it's the same type and `(have.mask & need.mask) === need.mask`, the game's rule, so an Arcanite rod covers all lesser rods. The guide weighs a missing tool's market cost like a pattern's, gets it at the first step that needs it (`step.tools`, `step.toolCost`; planned with that step's materials, so a rod is crafted, a hammer bought), adds the tool's recipe to the lessons, and starts from the tools your characters already have (TSM).
- **A profession plan is shown in stages, one per trainer rank** (Apprentice to 75, Journeyman to 150, Expert to 225, Artisan to 300; `SKILL_RANKS`), like gw2crafts' tiers. A step never crosses a rank's cap. Each stage has its recipes to learn, its own buy list (materials of its steps not yet done), its cost and a running total. Bought ticks are per stage (`boughtMaterials`: `"Rank:itemId"`), because the same material is often bought again for a later stage; the side list only adds up what's unticked and not owned, so there's one place to tick. The training line's character levels (10, 20, 35) are the classic ones. Trainer recipes and rank training name the trainer by the rank at that skill: up to Journeyman "any <Profession> trainer"; Expert and Artisan link up to two of your faction's NPCs titled "Expert/Artisan <Leatherworker>" (found once per Questie load by scanning NPC titles, `trainersTitled`, about 60 ms; read through `toRaw` so the scan isn't reactive). Cooking and First Aid have no ranked titles and stay generic. Hovering a step's item shows the recipe for one craft.
- **The profession list follows the character.** With two primary professions (gathering ones count), only its own guide-supported professions plus the secondary ones (Cooking, First Aid) are offered, without "(yours)"; otherwise its own come first marked "(yours)", then all others. "Compare professions" builds a fresh 1 → 300 plan for each listed profession (about 70 ms for all eight) and reads its cost at 150, 225 and 300.
- **The crafting tool does not persist its items.** "Craft all" in the gear plan feeds it; opened on its own it loads the selected character's craftable picks.
- **Vendor materials beat the AH unless the AH is more than 15% cheaper.** The Bartering perk takes 5% off per rank.
- **Hover maps are the game's own map art, fully explored, kept light** (about 55 KB per map, loaded only on hover). `tools/build-maps.js` draws the base art and then every explored-area overlay on top (`WorldMapOverlay`, skipping player-condition variants), so roads, towns and terrain show as on a discovered map. No POIs or flight points are added: the game has no map art with those. Drawn or SVG maps were rejected because they must look the same as in game.
- **Wowhead links go on names whose single source is clear:** quests, vendors and drop mobs. Materials like Light Leather have too many sources to link.

## Structure

SOLID, translated to a functional TypeScript + Vue code base (no classes, no DI container):

- **One job per module and per function.** Logic modules (`scoring`, `sources`, `upgrades`, `route`, `crafting-plan`, `profession-guide`) are typed and DOM-free. `ui/*.ts` turns their results into view rows and holds the page actions. Components only bind rows to markup, computeds call one `ui/` function each. A function that does several jobs gets split into named steps (`collectSourcesForCharacter` → quest context, item-data sources, Questie quests, Questie world sources).
- **Dependencies point down.** Logic never imports from `ui/` or a page, and a page module never imports another page's module: shared pieces get their own module (`tool-page.ts`, `ui/folder-controls.ts`, `ui/recipe-sources.ts`, the character helpers in `state.ts`). When lower code must trigger something above it, it takes a callback (`observeRanking(queueTooltipChecks)`, `runTooltipChecks(render)`, `sumMaterials(steps, pricing)`). No import cycles.
- **One answer to each question.** "Does this character have the profession / know the recipe / what's their skill" is `snapshotOf`, `professionOf`, `knowsRecipe` in `state.ts`; don't loop over `snapshot.professions` elsewhere.
- **Closed sets of strings are union types** (`SourceType`, `PlanMode`, `RecipeColor`), so a typo is a compile error.
- **Known debt:** logic modules still read the generated data from `window` (`FOREVER_RECIPES`, `GAME_RULES`, …) and the `state` singleton directly, so tests set globals (`resetPlanner`). Passing that data in would make the logic modules fully independent; do it when one of them is next reworked, not as a big bang.

A refactor must not change anything a player sees: compare the built site against the built `develop` on the same inputs (every slot's picks and cards in questing, dungeons and with a gold limit, the gear plan and paper doll after picking, the crafting page, and profession plans) and get 0 differences.

## Code conventions

- Plain named `function` declarations. No arrow functions, no ternaries, no anonymous callbacks; give callbacks names (`function isPhaseZero(row)`). No code comments.
- Build DOM with `createElement` and `textContent`, never `innerHTML` with data.
- English identifiers, descriptive names, no abbreviations.
- Guard only against real data gaps, such as Questie or TSM not being connected.
- Every plain data `<script>` and stylesheet URL carries `?build=__BUILD__`; Vite hashes the files it bundles. The deploy workflow builds with Vite, then stamps `__BUILD__` and `__VERSION__` (the latest tag) into `dist/*.html`.
- In TypeScript and Vue: the same naming and no-comments rules; named functions, no ternaries, logic in computed properties or functions rather than in templates, no watchers. Arrow functions only where Vue's API needs them.
- Dependencies are pinned exactly and must be at least two weeks old when added. TypeScript stays on 6.x while vue-tsc needs its JavaScript API.
- WoW files use CRLF line endings. Test every reader against a CRLF fixture.

## Tests and verification

- `npm test` runs `node:test` on `tests/*.test.mjs`, which import the TypeScript modules directly (Node strips the types, so modules may only use erasable TypeScript syntax and must import with `.ts` extensions); `tests/helpers/cbor.js` builds Questie fixtures. `tests/helpers/realm.mjs` loads the data scripts and the modules once into the real global scope (a module can't be reloaded per test, so `resetPlanner` resets state, caches and `FOREVER_ITEMS` instead); `run("…")` evaluates in that scope.
- `python3 -m unittest discover -s tests -p "test_*.py"` tests the data builder.
- Both run in CI before every deploy.
- For UI changes, run `npm run dev` (or `npm run build` and serve `dist/`) and check in a real browser. Playwright with a Battle.net client and a local Questie copy works well. Keep those scripts out of the repo.

## Branches and releases

- git-flow: `feature/*` merges into `develop` (`--no-ff`, "merges feature/x into develop").
- A release merges a `release/X.Y.Z` branch into `main` ("merges release/X.Y.Z into main") and is tagged `vX.Y.Z`.
- Pushing `main` publishes the site.
- Commit subjects are lowercase, third-person verb ("adds …", "fixes …"), with no body.
- Add a `CHANGELOG.md` entry for every release.
